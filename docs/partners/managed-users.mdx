A managed user is a record in your partner registry, one for each of your platform's customers. **It is not a login, and it does not own anything.** Everything you create through the API still belongs to your administering account, and the link between a customer and their compositions is yours to keep.

## Overview

A managed user is:

- A record with a Widgetic `id` (a UUID), your own `externalId` (unique among your managed users, for example your customer number) and a free-form `metadata` object.
- Visible only to you. A record that belongs to another partner answers `404`, never `403`, so nothing about other partners can be learned.

A managed user is not:

- **A login.** It has no password, no API key and no session. You cannot act "as" a managed user.
- **An owner.** Compositions, widgets, uploads, credits, storage and the list of allowed websites belong to your administering account. A composition has no field that names a managed user.
- **A billing unit.** There are no per-customer credits, storage or invoices. You are invoiced once, for the contract. See [Credits & Billing](/docs/partners/credits-billing).

The examples on this page are for your server. Keep the key in an environment variable, such as `WIDGETIC_PARTNER_KEY`.

## Creating Managed Users

Create a managed user for each of your platform's customers. Send the `Idempotency-Key` header, and note that this request body uses snake_case while answers use camelCase:

```bash
curl -sS -X POST "https://api.widgetic.com/v1/managed-users" \
  -H "Authorization: Bearer $WIDGETIC_PARTNER_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{
    "external_id": "your-platform-user-123",
    "metadata": { "firstName": "John", "lastName": "Doe", "email": "john@example.com", "role": "editor" }
  }'
```

```json
{
  "success": true,
  "data": {
    "id": "3f0c9a52-8e0a-4a52-9d52-5d8a1f1b7c10",
    "managerId": "<your administering account id>",
    "externalId": "your-platform-user-123",
    "metadata": { "firstName": "John", "lastName": "Doe", "email": "john@example.com", "role": "editor" },
    "createdAt": "2026-10-02T20:10:00.000Z",
    "updatedAt": "2026-10-02T20:10:00.000Z"
  }
}
```

- `201` on success. `409` if you already have a managed user with that `external_id`. `400` if `external_id` is missing.
- `manager_id` is optional and defaults to you. Leave it out: you can only use your own, and another account's id is refused with `403`.
- Use camelCase keys inside `metadata`. The API converts every key in every answer to camelCase, so `company_name` would come back as `companyName`.

<Note>
  `POST /managed-users` and `PUT /managed-users/{id}` need an `Idempotency-Key` header (see [Idempotency](/docs/reference/idempotency)). The `ManagedUsersApi` in the `@widgetic/api-sdk` package on npm today (1.0.22) does not add one for you, so call these two with plain HTTP, or pass the header yourself.
</Note>

## Listing Managed Users

`GET /managed-users` returns your managed users, newest first. The query takes `page`, `size` (at most 100) and `sort` (default `created_at:desc`). The answer has `data`, a list, and `meta` with `page`, `size` and `total`:

```bash
curl -sS -H "Authorization: Bearer $WIDGETIC_PARTNER_KEY" \
  "https://api.widgetic.com/v1/managed-users?page=1&size=20"
```

## Getting a Specific User

`GET /managed-users/{id}` returns one record:

```bash
curl -sS -H "Authorization: Bearer $WIDGETIC_PARTNER_KEY" \
  "https://api.widgetic.com/v1/managed-users/$MANAGED_USER_ID"
```

There is no search by `external_id`. Keep the Widgetic `id` in your own database next to your customer id, so you never need to look a customer up by scanning pages.

## Updating Managed Users

`PUT /managed-users/{id}` changes the `external_id` and/or the `metadata`. It needs an `Idempotency-Key`. The `metadata` is **replaced as a whole**, so send all of it:

```bash
curl -sS -X PUT "https://api.widgetic.com/v1/managed-users/$MANAGED_USER_ID" \
  -H "Authorization: Bearer $WIDGETIC_PARTNER_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{ "metadata": { "firstName": "John", "lastName": "Smith", "role": "admin" } }'
```

## Deleting Managed Users

`DELETE /managed-users/{id}` removes the record and answers `200` with `{"message": "...", "id": "..."}`. It does not delete anything else: delete the customer's compositions yourself (`DELETE /compositions/{id}`) when they leave.

## Managed User Entitlements

Entitlements are read only: Widgetic sets them and you cannot change them through the API.

- `GET /entitlements/managed-users/{managedUserId}` lists the entitlements of one managed user. The answer has `data.managedUserId` and `data.entitlements`.
- `GET /entitlements/partners/{partnerId}` lists what your partner record is entitled to.
- Both accept `feature`, `source` and `includeExpired` as filters.
- Each entitlement has a `feature`, a `value`, a `source` (`subscription`, `contract`, `manual`, `marketplace` or `addon`) and `expiresAt`.

```bash
curl -sS -H "Authorization: Bearer $WIDGETIC_PARTNER_KEY" \
  "https://api.widgetic.com/v1/entitlements/managed-users/$MANAGED_USER_ID"
```

## Keep Your Own Mapping

Widgetic does not link customers to compositions, so your database must. A minimal shape:

- A customers table: your customer id, and the Widgetic managed-user `id`.
- A widgets table: your customer id, the Widgetic composition `id`, and the Widgetic `widgetId` it is built on.
- Put the customer in the composition name as well, for example `your-platform-user-123 / homepage slider`, so a person looking in the Widgetic dashboard can tell whose it is.

```sql
-- In your database
CREATE TABLE widgetic_user_mapping (
  platform_user_id VARCHAR PRIMARY KEY,
  widgetic_managed_user_id UUID,
  created_at TIMESTAMP
);
```

## User Metadata Schema

The `metadata` field is flexible, but we recommend including:

```typescript
interface ManagedUserMetadata {
  // Identity
  firstName?: string;
  lastName?: string;
  email?: string;
  avatarUrl?: string;

  // Permissions you track on your side
  role?: 'viewer' | 'editor' | 'admin';
  permissions?: string[];

  // Your custom fields
  teamId?: string;
  department?: string;
  plan?: string;

  // Any other JSON-serializable data. Use camelCase keys
  [key: string]: any;
}
```

Widgetic stores this object and gives it back. It does not act on it: a `role` here does not change what anyone can do in Widgetic.

  </Accordion>

  <Accordion title="Handle User Deletion">
    When a user leaves your platform, delete their compositions first, then their managed user. Deleting a managed user does not delete anything else.

## Not Available Yet

- Signing in as, or getting a key for, a managed user.
- Linking a composition, an upload or a charge to a managed user.
- Looking up a managed user by `external_id`.
- Changing entitlements yourself.

## Error Handling

Common errors when working with managed users. Branch on `error.code` in the answer (see [Errors](/api-reference/errors)):

| Status | Description |
|--------|-------------|
| 400 | `external_id` is missing, or the `Idempotency-Key` header is missing |
| 403 | The caller is not a partner, or `manager_id` names another account |
| 404 | The managed user does not exist, or belongs to another partner |
| 409 | A managed user with this `external_id` already exists |
