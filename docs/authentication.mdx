The Widgetic API uses Bearer token authentication. All requests must include an `Authorization` header with your API key or editor session token.

## Authentication Methods

### API Keys (Server-Side)

API keys are the recommended authentication method for server-side applications. They provide persistent access without expiration.

```bash
Authorization: Bearer wdg_org_your_api_key_here
```

You make a key in the dashboard: open the workspace, then **Settings → API keys** (the owner of a workspace opens that page). A key you make there is a **workspace key**. It starts with `wdg_org_`, acts as that workspace and works in it only, and it does not follow the workspace you have open afterwards, so make one key for each workspace you work in. `GET /tokens/validate` says which workspace a key works in (`data.workspace`: its `id` and `name`).

A key can be limited to what its application needs, a build server for example: see [Limit what a key can do](#limit-what-a-key-can-do). Only a person signed in on widgetic.com can make a key (a key cannot make another key), and the workspace needs a paid plan to hold keys (the home workspace of a [partner](/docs/partners/overview#partner-api-key) needs none: it pays by the invoices of its contract).

<Note>
  A key that starts with `wgt_usr_` is a personal key from before workspace keys. Personal keys are no longer accepted: a request that carries one is refused with `401`, and the message says to make a workspace key. Make a workspace key, send that instead, and delete the old one.
</Note>

### Editor Sessions (For Customer Browsers)

To run Widgetic's editors inside your own page for one of your customers, mint a short-lived [editor session](/docs/partners/editor-sessions) on your server and pass that session token to the browser.

```bash
Authorization: Bearer wgt_eds_your_editor_session_token_here
```

## API Key Types and Access Levels

Your API key prefix determines your role and what endpoints you can access:

| Key Prefix | Role | Access Level | Use Case |
|------------|------|--------------|----------|
| `wdg_org_` | Workspace | `user`; `partner` in the home workspace of a partner | The key of a workspace, made in the dashboard: it acts as that workspace, in that workspace only. In a partner's home workspace it acts as the partner |
| `wgt_usr_` | None (retired) | None | A personal key from before workspace keys. It is no longer accepted: every request that carries one is refused with `401`. Make a workspace key instead |
| `wgt_prt_` | Partner | `partner` | White-label integrations: the key of the account that administers a partner |
| `wgt_adm_` | Admin | `admin` | Internal administration |

## Understanding Access Levels

Each API endpoint specifies an `x-access-level` that determines which roles can access it:

- **`public`**: Any authenticated user can access (any key type)
- **`user`**: Requires user-level access or higher
- **`partner`**: Requires partner-level access or higher
- **`admin`**: Requires admin-level access only

<Note>
  The `x-access-level` is a **role gate**, not a visibility gate. All public endpoints appear in the documentation, but your access depends on your key type.
</Note>

## Limit What a Key Can Do

A key made without a limit has **full access**: it does everything its owner can, and so does every key made before limits existed. A key you put on a build server, or in a partner's backend, needs only the part of the API it uses. Limit it, and a leaked key can do no more than that.

You choose the limit when you make the key, in the dialog on **Settings → API keys**: Full access, Content, Read only or Custom, where you tick what the key may do. The names below are the ones the dialog shows. A partner account that makes its keys with `POST /users/{id}/keys` (see [Security](/resources/security#making-rotating-and-deleting-keys)) sends them as a `preset` or a list of `scopes`, never both:

| Preset | What the key may do |
|--------|---------------------|
| `read_only` | Looks at everything its owner holds and changes nothing. It holds `content:read`, `partner:read`, `billing:read` and `account:read`. |
| `content` | Builds and manages widgets and compositions, and runs the AI. It holds `content:read`, `content:write` and `generate`, and touches no billing, no people and no partners. |
| `full_access` | Everything its owner may do. A key made with neither a preset nor scopes is this. |

When a preset is not enough, name the scopes you want:

| Scope | What it lets a key do |
|-------|-----------------------|
| `content:read` | Read widgets, compositions, canvases, projects, folders, uploads, translations and the analytics of your content. |
| `content:write` | Create, change, publish and delete the same. Includes `content:read`. |
| `generate` | Run the AI that builds widgets and compositions, and follow or cancel what it is doing. This spends credits. |
| `partner:read` | Read managed users, what they spent, presets, the contract and the storage destination (partners). |
| `partner:write` | Create, change and delete managed users and presets (partners). Includes `partner:read`. |
| `billing:read` | Read credits, usage, invoices, subscriptions and payment methods. |
| `billing:write` | Buy credits, pay invoices, change a subscription or a payment method. Includes `billing:read`. |
| `account:read` | Read the profile, organizations and members, allowed domains, notices, the names of API keys and the [Brand Kit](/docs/partners/brand-kit). |
| `account:write` | Change the profile, organizations and members, allowed domains and integrations. Includes `account:read`. |

- **Writing includes reading.** Naming `content:write` gives `content:read` too, and the same goes for the other `write` scopes. A list that names every scope makes a key with full access.
- **Scopes only narrow.** A limited key still needs what its owner needs: the role, the plan and, for a [partner](/docs/partners/account-status), an account in force.
- **The partner scopes (`partner:read`, `partner:write`) are for a partner's home workspace.** Only there does a workspace key act as the partner, so only there does the dialog offer them; in any other workspace they would open nothing.
- **The limit is fixed when the key is made.** To widen it, make a new key and delete the old one.
- **A limited key cannot make itself a bigger one.** Making, changing and deleting keys, exchanging tokens, signing in and the administration routes need full access.
- **Changing the Brand Kit needs full access**, because a change reshapes every widget the account makes from then on. A key with `account:read` may look at it. See [Brand Kit](/docs/partners/brand-kit).
- **The MCP server needs full access.** `https://mcp.widgetic.com` hands an assistant every tool your account has, so only a key made with full access opens it, and a limited key is refused with `403`. See [Authentication for AI assistants](/docs/agents/authentication#api-keys).
- **A partner's backend needs three scopes to start an editor session** for a managed user: `partner:write`, `content:write` and `generate` together. See [Editor Sessions](/docs/partners/editor-sessions#make-a-session).

A request outside the scopes of the key is refused with `403` and the code `API_KEY_SCOPE_MISSING`. `error.details.missingScopes` lists what a new key needs, and `error.details.fullAccessRequired` is `true` when no list of scopes would have been enough:

```json
{
  "success": false,
  "error": {
    "code": "API_KEY_SCOPE_MISSING",
    "message": "This API key may not do this: it lacks the content:write scope (it holds content:read, partner:read, billing:read, account:read). The scopes of a key cannot be changed once it is made, so make a new key that includes them.",
    "details": {
      "missingScopes": ["content:write"],
      "fullAccessRequired": false
    }
  }
}
```

<Note>
  These scopes belong to the key and last as long as it does. To give a customer's browser limited, short-lived access to only that customer's content, mint an [editor session](/docs/partners/editor-sessions) on your server instead.
</Note>

## Validating Tokens

You can validate a token to check its status and associated permissions:

```bash
curl -X GET "https://api.widgetic.com/v1/tokens/validate" \
  -H "Authorization: Bearer YOUR_TOKEN"
```

Response:
```json
{
  "success": true,
  "data": {
    "valid": true,
    "tokenType": "api_key",
    "scopes": ["content:read", "content:write"],
    "userId": "123e4567-e89b-12d3-a456-426614174000",
    "expiresAt": null
  }
}
```

## Best Practices

<AccordionGroup>
  <Accordion title="Keep API Keys Secure">
    - Never expose API keys in client-side code
    - Use environment variables to store keys
    - Rotate keys periodically
    - Use the token exchange flow for browser applications
  </Accordion>
  
  <Accordion title="Use Appropriate Key Types">
    - Make one workspace key (`wdg_org_`) for each workspace you work in, and one for each application
    - Limit a key to what its application needs: Read only for a report, Content for a build server
    - A personal `wgt_usr_` key from before workspace keys no longer works: make a workspace key, switch your servers over to it, then delete the old one
    - For a partner integration, make the key in your partner's home workspace (`wdg_org_`): it acts as your partner. A `wgt_prt_` key does the same
  </Accordion>
  
  <Accordion title="Handle Token Expiration">
    - JWT tokens expire after a set period
    - Implement token refresh logic in your application
    - Use the SDK's async token provider for automatic handling
  </Accordion>
</AccordionGroup>

## Error Responses

When authentication fails, you'll receive one of these responses:

| Status | Code | Description |
|--------|------|-------------|
| 401 | `UNAUTHORIZED` | Missing or invalid authentication token |
| 403 | `FORBIDDEN` | Token valid but insufficient permissions |

Example error response:
```json
{
  "success": false,
  "error": {
    "code": "FORBIDDEN",
    "message": "Insufficient permissions for this endpoint",
    "correlationId": "req_123e4567-e89b-12d3-a456-426614174000"
  }
}
```
