This guide covers security best practices when integrating with the Widgetic API.

## API Key Security

### Storage

<Warning>
  Never expose API keys in client-side code, version control, or public repositories.
</Warning>

**Do:**
- Store keys in environment variables
- Use secrets management services (AWS Secrets Manager, Vault, etc.)
- Rotate keys periodically

**Don't:**
- Commit keys to git
- Include keys in frontend bundles
- Share keys via unencrypted channels

### Key Types

| Prefix | Security Level | Use Case |
|--------|----------------|----------|
| `wgt_usr_` | User | Personal server-side use |
| `wdg_org_` | Organization | Shared server-side use |
| `wgt_prt_` | Partner | White-label integrations |

### Making, Rotating and Deleting Keys

You make and manage your own keys. In the dashboard, open Workspace settings → API keys. With the API, use the key calls below. `{id}` is your own account id, which `GET /tokens/validate` returns as `data.userId`. Your plan must include API access.

- `GET /users/{id}/keys` lists your keys, and `POST /users/{id}/keys` makes one (send an `Idempotency-Key`). The secret is in the answer once, in `key`, and cannot be shown again. An account can have 25 keys.
- `PUT /users/{id}/keys/{keyId}` renames a key or switches it off with `isActive: false`, and `DELETE /users/{id}/keys/{keyId}` deletes it.
- `GET /users/{id}/api-keys/{keyId}/logs` shows what a key was used for.

To rotate a key, make the new one, switch your servers over, then delete the old one. A key that is switched off or deleted is refused at once by the server that took the request, and within a minute by the others.

<Warning>
  A key can make other keys. If a key leaks, delete it, then list your keys and delete any you did not make.
</Warning>

## Client-Side Authentication

For browser applications, use the token exchange flow:

```typescript
// Server-side: Exchange API key for limited token
app.get('/api/widgetic-token', async (req, res) => {
  const tokens = new TokensApi(process.env.WIDGETIC_API_KEY);
  
  const { token, expiresAt } = await tokens.exchangeToken({
    scopes: ['read:widgets', 'write:compositions'],
    expiresIn: 3600 // 1 hour
  });
  
  res.json({ token, expiresAt });
});

// Client-side: Use the limited token
const api = new WidgetsApi({
  apiKey: async () => {
    const res = await fetch('/api/widgetic-token');
    const { token } = await res.json();
    return token;
  }
});
```

## Domain Validation

You can limit the websites an embedded widget may appear on. If you list nothing, the widget works everywhere.

1. Go to Dashboard → Settings → Domains (for a team workspace, use that workspace's domain settings)
2. Add each website: `example.com` also covers `www.example.com`, and `*.example.com` covers the domain and every subdomain
3. Add `localhost` too while you test on your own machine

You can also keep the list with the API, using your own account id as `{id}`. `GET /users/{id}/workspace/domains` reads it, `POST` adds a website with the body `{ "domain": "example.com" }`, `PUT /users/{id}/workspace/domains/{domainId}` changes one, and `DELETE` removes one. A list holds up to 50 websites, and a change applies within about 15 seconds.

Once a list exists, the lookup that returns a widget's content answers `403` with the code `DOMAIN_NOT_ALLOWED` to a page on any other website, and the widget's frame page asks the browser not to show it anywhere else. Widgetic's own sites always work, and a list that cannot be read never blocks a widget.

If you use the Partner API, the `allowedDomains` of your partner account is added to the list of the person who administers it, and applies to the widgets made with your API keys.

<Note>
  A domain list keeps your widgets off other people's pages. It is not access control: the content of a published widget can still be requested by anyone who has its ID, using a plain HTTP request that names no website for the check to read. Do not rely on it to keep content private.
</Note>

<Warning>
  The `<widgetic>` embed script does not honour the refusal yet: it can fall back to a copy of the widget on Widgetic's CDN and draw it anyway. When you need the list to hold, use the frame (`https://api.widgetic.com/embed/compositions/{id}/frame`).
</Warning>

## Request Signing

For webhook callbacks, verify the signature:

```typescript
import crypto from 'crypto';

function verifyWebhookSignature(
  payload: string,
  signature: string,
  secret: string
): boolean {
  const expected = crypto
    .createHmac('sha256', secret)
    .update(payload)
    .digest('hex');
  
  return crypto.timingSafeEqual(
    Buffer.from(signature),
    Buffer.from(expected)
  );
}

app.post('/webhook', (req, res) => {
  const signature = req.headers['x-webhook-signature'];
  
  if (!verifyWebhookSignature(req.body, signature, WEBHOOK_SECRET)) {
    return res.status(401).send('Invalid signature');
  }
  
  // Process webhook
});
```

## Rate Limiting

Protect your integration from abuse:

```typescript
import rateLimit from 'express-rate-limit';

const limiter = rateLimit({
  windowMs: 60 * 1000, // 1 minute
  max: 100, // Limit each IP to 100 requests per window
  message: 'Too many requests, please try again later'
});

app.use('/api/widgetic', limiter);
```

## Data Protection

### Sensitive Data

Don't store sensitive user data in widget configurations:

```typescript
// ❌ Bad
widget.config = {
  apiKey: 'secret',
  password: 'user-password'
};

// ✅ Good
widget.config = {
  userId: 'user-uuid',
  settings: { theme: 'dark' }
};
```

### Audit Logging

Log API interactions for security auditing:

```typescript
async function logApiCall(
  action: string,
  resourceId: string,
  userId: string
) {
  await db.auditLog.create({
    action,
    resourceId,
    userId,
    timestamp: new Date(),
    ip: req.ip
  });
}
```

## Compliance

### GDPR

When handling EU user data:

- Implement data deletion on user request
- Provide data export functionality
- Document data processing purposes

```typescript
// Delete user data
await widgetic.deleteUser({ userId });

// Export user data
const userData = await widgetic.exportUserData({ userId });
```

### SOC 2

Widgetic maintains SOC 2 Type II compliance. For compliance documentation, contact [security@widgetic.com](mailto:security@widgetic.com).

## Security Checklist

<Accordion title="API Key Management">
- [ ] Keys stored in environment variables
- [ ] Keys rotated quarterly
- [ ] Separate keys for dev/staging/production
- [ ] Access logged and monitored
</Accordion>

<Accordion title="Client Security">
- [ ] Token exchange for browser apps
- [ ] Short token expiration (1-24 hours)
- [ ] Domain validation enabled
- [ ] CSP headers configured
</Accordion>

<Accordion title="Webhook Security">
- [ ] Signature verification implemented
- [ ] HTTPS only
- [ ] Idempotency for retries
- [ ] Timeout handling
</Accordion>

## Reporting Vulnerabilities

Found a security issue? Report it responsibly:

- Email: [security@widgetic.com](mailto:security@widgetic.com)
- PGP key available on request
- Response within 48 hours

We appreciate responsible disclosure and may offer bug bounties for significant findings.
