This guide covers security best practices when integrating with the Widgetic API.

## API Key Security

### Storage

<Warning>
  Never expose API keys in client-side code, version control, or public repositories.
</Warning>

**Do:**
- Store keys in environment variables
- Use secrets management services (AWS Secrets Manager, Vault, etc.)
- Rotate keys periodically

**Don't:**
- Commit keys to git
- Include keys in frontend bundles
- Share keys via unencrypted channels

### Key Types

| Prefix | Security Level | Use Case |
|--------|----------------|----------|
| `wgt_usr_` | User | Personal server-side use |
| `wdg_org_` | Organization | Shared server-side use |
| `wgt_prt_` | Partner | White-label integrations |

### Making, Rotating and Deleting Keys

You make and manage your own keys. In the dashboard, open Workspace settings → API keys. With the API, use the key calls below. `{id}` is your own account id, which `GET /tokens/validate` returns as `data.userId`. Your plan must include API access.

- `GET /users/{id}/keys` lists your keys, with what each is limited to (`preset` and `scopes`).
- `POST /users/{id}/keys` makes one (send an `Idempotency-Key`). **Only a person signed in on widgetic.com can make a key**, so make keys in the dashboard: a request made with an API key or an SDK token is refused with `403`. The secret is in the answer once, in `key`, and cannot be shown again. An account can have 25 keys. Send a `preset` (`read_only`, `content` or `full_access`) or a list of `scopes` to limit what the key can do, and neither for a key with full access. See [Limit what a key can do](/docs/authentication#limit-what-a-key-can-do).
- `PUT /users/{id}/keys/{keyId}` renames a key or switches it off with `isActive: false`. Switching a key back on needs a person signed in too. `DELETE /users/{id}/keys/{keyId}` deletes it.
- `GET /users/{id}/api-keys/{keyId}/logs` shows what a key was used for.

To rotate a key, make the new one in the dashboard, switch your servers over, then delete the old one. A key that is switched off or deleted is refused at once by the server that took the request, and within a minute by the others. The limit of a key cannot be changed once it is made: to widen or narrow it, rotate the key the same way.

<Warning>
  A key cannot make another key, so a leaked key cannot be used to get back in after you revoke it. If a key leaks, delete it (in the dashboard, or with another key) and make a new one in the dashboard.
</Warning>

## Client-Side Authentication

For browser applications, use the token exchange flow:

```typescript
// Server-side: Exchange API key for limited token
app.get('/api/widgetic-token', async (req, res) => {
  const tokens = new TokensApi(process.env.WIDGETIC_API_KEY);
  
  const { token, expiresAt } = await tokens.exchangeToken({
    exchangeTokenRequest: {
      scopes: ['widgets:read', 'compositions:write'],
      expiresIn: 3600 // 1 hour
    }
  });
  
  res.json({ token, expiresAt });
});

// Client-side: Use the limited token
const api = new WidgetsApi({
  accessToken: async () => {
    const res = await fetch('/api/widgetic-token');
    const { token } = await res.json();
    return token;
  }
});
```

The scopes are recorded in the token, but the API does not check them on each call yet, so treat the token as having the access of the key that made it until it expires. See [Authentication](/docs/authentication) for the scopes you can ask for.

<Note>
  To run Widgetic's own editors in a browser for one of your customers, use an [editor session](/docs/partners/editor-sessions) rather than this flow. A session reaches only that customer's content, only the calls the editors need, and can be bound to your page and ended at any time.
</Note>

## Domain Validation

You can limit the websites an embedded widget may appear on. If you list nothing, the widget works everywhere.

1. Open Allowed Domains in the dashboard (for a team workspace, use that workspace's settings; only its admins and owners can change the list)
2. Add each website: `example.com` also covers `www.example.com`, and `*.example.com` covers the domain and every subdomain
3. Leave `localhost` out: a page on your own machine always works, however short the list is (see below)

You can also keep the list with the API, using your own account id as `{id}`. `GET /users/{id}/workspace/domains` reads it, `POST` adds a website with the body `{ "domain": "example.com" }`, `PUT /users/{id}/workspace/domains/{domainId}` changes one, and `DELETE` removes one. A list holds up to 50 websites, and a change applies within about 15 seconds.

Once a list exists, the lookup that returns a widget's content answers `403` with the code `DOMAIN_NOT_ALLOWED` to a page on any other website, and the widget's frame page asks the browser not to show it anywhere else. Widgetic's own sites always work, and so does your own machine. The lookup never refuses a page on `localhost`, on `127.0.0.1` (or any address from `127.0.0.0` to `127.255.255.255`), on `[::1]` or on a name under `.localhost`, on any port, and the widget's frame page may be shown by `localhost`, `127.0.0.1` and names under `.localhost`, on any port, over `http` or `https`. You can build and test an integration without listing your laptop: only the person who runs such a page can see it, so listing it would protect nothing. A list that cannot be read never blocks a widget.

If you use the Partner API, the `allowedDomains` of your partner account is added to the list of the person who administers it, and applies to the widgets made with your API keys.

<Note>
  A domain list keeps your widgets off other people's pages. It is not access control: the content of a published widget can still be requested by anyone who has its ID, using a plain HTTP request that names no website for the check to read. Do not rely on it to keep content private.
</Note>

<Note>
  The `<widgetic>` embed script stops at the refusal: it draws nothing, sets `data-widgetic-refused="DOMAIN_NOT_ALLOWED"` on the element, and writes one warning to the browser console for each widget. It does not fall back to a copy of the widget on Widgetic's CDN.
</Note>

## Request Signing

<Warning>
  **Not available yet.** Widgetic does not send webhooks to your server today (see [Integrations](/resources/integrations#webhooks)), so there is no signature to check. The sketch below shows the check you would write once it does.
</Warning>

For webhook callbacks, verify the signature:

```typescript
import crypto from 'crypto';

function verifyWebhookSignature(
  payload: string,
  signature: string,
  secret: string
): boolean {
  const expected = crypto
    .createHmac('sha256', secret)
    .update(payload)
    .digest('hex');
  
  return crypto.timingSafeEqual(
    Buffer.from(signature),
    Buffer.from(expected)
  );
}

app.post('/webhook', (req, res) => {
  const signature = req.headers['x-webhook-signature'];
  
  if (!verifyWebhookSignature(req.body, signature, WEBHOOK_SECRET)) {
    return res.status(401).send('Invalid signature');
  }
  
  // Process webhook
});
```

## Rate Limiting

Protect your integration from abuse:

```typescript
import rateLimit from 'express-rate-limit';

const limiter = rateLimit({
  windowMs: 60 * 1000, // 1 minute
  max: 100, // Limit each IP to 100 requests per window
  message: 'Too many requests, please try again later'
});

app.use('/api/widgetic', limiter);
```

## Data Protection

### Sensitive Data

Don't store sensitive user data in widget configurations:

```typescript
// ❌ Bad
widget.config = {
  apiKey: 'secret',
  password: 'user-password'
};

// ✅ Good
widget.config = {
  userId: 'user-uuid',
  settings: { theme: 'dark' }
};
```

### Audit Logging

Log API interactions for security auditing:

```typescript
async function logApiCall(
  action: string,
  resourceId: string,
  userId: string
) {
  await db.auditLog.create({
    action,
    resourceId,
    userId,
    timestamp: new Date(),
    ip: req.ip
  });
}
```

## Compliance

### GDPR

When handling EU user data:

- Implement data deletion on user request
- Provide data export functionality
- Document data processing purposes

If you keep [managed users](/docs/partners/managed-users) for your customers, Widgetic holds a record for each one. You can read a record and delete it:

```bash
# Read the record of one customer
curl -sS -H "Authorization: Bearer $WIDGETIC_API_KEY" \
  "https://api.widgetic.com/v1/managed-users/$MANAGED_USER_ID"

# Delete it
curl -sS -X DELETE -H "Authorization: Bearer $WIDGETIC_API_KEY" \
  "https://api.widgetic.com/v1/managed-users/$MANAGED_USER_ID"
```

Deleting the record removes the managed user, not what you filed under it. The compositions, widgets and uploads stay in your account, and lose only their `managedUserId` label. To erase a customer's content as well, list it with the `managedUserId` filter and delete it first, then delete the record (see [Managed Users](/docs/partners/managed-users#filing-content-under-a-managed-user)).

### SOC 2

Widgetic maintains SOC 2 Type II compliance. For compliance documentation, contact [security@widgetic.com](mailto:security@widgetic.com).

## Security Checklist

<Accordion title="API Key Management">
- [ ] Keys stored in environment variables
- [ ] Keys rotated quarterly
- [ ] Separate keys for dev/staging/production
- [ ] Access logged and monitored
</Accordion>

<Accordion title="Client Security">
- [ ] Token exchange for browser apps
- [ ] Short token expiration (a token lasts at most 1 hour)
- [ ] Domain validation enabled
- [ ] CSP headers configured
</Accordion>

<Accordion title="Webhook Security (not available yet)">
- [ ] Signature verification implemented
- [ ] HTTPS only
- [ ] Idempotency for retries
- [ ] Timeout handling
</Accordion>

## Reporting Vulnerabilities

Found a security issue? Report it responsibly:

- Email: [security@widgetic.com](mailto:security@widgetic.com)
- PGP key available on request
- Response within 48 hours

We appreciate responsible disclosure and may offer bug bounties for significant findings.
